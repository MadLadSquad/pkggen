# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running pkggen

The virtualenv lives in `src/venv/`. Set it up once:
```sh
cd src && python3 -m venv venv && source venv/bin/activate && pip install -r requirements.txt
```

Run directly (no install required):
```sh
cd src && PKGGEN_RUN_PATH=../example python3 pkggen/pkggen <command>
```

Or install as a CLI tool (pulls in the dependencies; works on every OS):
```sh
pip install ./src      # copies generators/ into the package, as pkggen/generators
pip install -e ./src   # editable: uses the checkout's generators/, so edits apply right away
# then from any directory with a pkggen.yaml:
pkggen <command>
```

The CLI is `src/pkggen/cli.py` (the `pkggen.cli:main` console script); `src/pkggen/pkggen` is a launcher that runs it from a checkout. The modules import each other by plain name (`import utils`), so `cli.py` puts its folder on `sys.path` first. `src/setup.py` bundles `generators/` in `build_py` (skipped for editable installs) and adds it to sdists, so wheels built from an sdist have it too.

Available commands: `generate [-p <packages>] [-d <distributions>]`, `gen-repo <distribution> [-o <dir>] [-f]`, `test [-p <packages>] [-d <distributions>] [-t <targets>] [-j <n>] [--engine podman|docker] [--keep]`, `deploy [-p <packages>] [-d <distributions>] [-t <targets>] [--skip-tests] [--dry-run]`, `repology <project> [-j] [-i]`, `version`.

## Running tests

```sh
pip install -r src/requirements-dev.txt   # pytest + responses, on top of requirements.txt
python -m pytest                           # from the repository root; offline, ~20 s
python -m pytest --live                    # also hit the real GitHub/repology APIs (or PKGGEN_TEST_LIVE=1; GITHUB_TOKEN avoids rate limits)
python -m pytest --containers              # also build in real podman/docker containers (or PKGGEN_TEST_CONTAINERS=1; needs the network)
python -m pytest tests/core/test_install.py # pip-installs pkggen (normal + editable) into a venv, offline, and runs it
python -m pytest --update-golden           # rewrite tests/golden/ after an intended output change
```

`tests/` mirrors the code: `core/` (CLI, `utils`, `gen_repo`, `generate`, `testing`, `containers`, `deploy`, repology), `repositories/`, `generation/`, `dependencies/`, `packaging/` (`test_dependencies.py`: picking and rendering `dependencies`), `testing/`, `deployment/` (real `git` and `ssh-keygen`, with local bare repositories as the upstreams), `e2e/` (the full `gen-repo` + `generate` pipeline on a copy of `example/`, all 12 packages with their committed templates and seed files, compared against `tests/golden/example.snapshot`), `live/` and `containers/` (`pkggen test` with a real engine, which sees the user's `CONTAINER_HOST`/`DOCKER_HOST` and Podman configuration through the `real_engine` fixture, so on macOS/Windows it reuses the `pkggen` machine; `PKGGEN_TEST_CONTAINERS_TARGETS` picks the releases or `all`, `PKGGEN_TEST_CONTAINERS_ENGINE` the engine, `PKGGEN_TEST_CONTAINERS_LOGS` a folder to copy the logs to). `.github/workflows/tests.yaml` runs the offline tests on Linux, macOS and Windows on every push and pull request. Run it by hand (workflow_dispatch) to also run the live tests, or the container tests on `ubuntu-latest` with Podman and Docker (the `targets` input picks the releases; the logs are uploaded as artifacts). Hosted macOS/Windows runners can't run a Linux VM, so the container tests only run on Linux.

- Tests never touch the user's config or `example/` (`example_project` copies it without `pkggen-build/`, the output of runs in the real example): an autouse fixture points `XDG_CONFIG_HOME`/`APPDATA` at a temp dir (so managed SSH keys land there too), points `GIT_CONFIG_GLOBAL` at a gitconfig in it that only sets `init.defaultBranch = main` (with `GIT_CONFIG_NOSYSTEM=1`), hides `CONTAINER_HOST`/`DOCKER_HOST`, `PKGGEN_CACHE_DIR`, `GNUPGHOME`, the AWS keys and the deployment variables below, and `example_project` works on a copy. The only exception is the real container test: its `real_engine` fixture links the user's `<config dir>/containers` into the temp dir and restores those two variables, so the real engine uses the user's machines and connections (pkggen's own secrets stay isolated).
- Generators run either in-process via `tests.support.helpers.load_generator(layer, name)` (swaps in that layer's `lib`; modules are registered in `sys.modules` under a unique name, which the deployment lib's `load_hook()` relies on), or as real subprocesses via `run_generator()` / `run_cli()`.
- The `s3` generator is tested against `FakeS3` in `tests/deployment/test_s3.py` (an in-memory bucket behind `responses` callbacks that checks signatures' presence, `Content-MD5` and the payload hash); signing tests make a throwaway ed25519 key with the real `gpg` (skipped without it).
- HTTP is mocked with `responses`: the `http` fixture in-process, `http_subprocess(routes)` for subprocesses (via `tests/support/http_shim/sitecustomize.py`, enabled by `PKGGEN_TEST_HTTP`; it also puts the shim on `PYTHONPATH`, so subprocesses the code under test starts itself are mocked too). Unmatched requests fail, so nothing reaches the network. Canned GitHub data for the example packages is in `tests/support/example.py`. Repology's answers for the example's dependencies are recorded in `tests/support/data/repology.json` (real shapes, trimmed to `distributions.yaml`'s releases; `tests/support/repology.py` serves them and builds packaging-job entries); `python -m tests.support.record_repology <project>...` adds projects (`--refresh` fetches them again, `--new-releases` only adds the releases the file doesn't have yet, e.g. after adding a distribution; without names, for every recorded project).
- Container engines are faked by `tests/support/fake_engine.py` (the `fake_engine` fixture sets `PKGGEN_TEST_ENGINE`): it records every command, keeps a fake file system per container for `cp`, fails steps containing `FAKE_FAIL`, records `chmod +x` lines so `exec … find … -perm -u+x` can list them (also on Windows; `fail_find` in its config makes that fail) and emulates `podman machine`. Patch `containers.host_platform` to test the VM paths.
- Tests that expose known bugs are marked `xfail(strict=True)` with the reason; fixing the bug makes them fail until the mark is removed.

## Intended design (target, not yet implemented)

This section is the author's plan for pkggen. The code does **not** match it yet — see "Current state vs. intended design" below and the "Architecture" section for what exists today.

pkggen takes inspiration from funtoo-metatools but extends the idea to the entire desktop application packaging lifecycle: repository creation → fetching → packaging → testing → deployment.

**Cross-platform requirement:** every stage except testing and deployment (i.e. repository creation, fetching and packaging) must run on any OS, including non-Linux ones (Windows, macOS, BSDs). Generators must not depend on the host being the target distribution or on distro tools (`rpmbuild`, `reprepro`, `createrepo_c`, …) or shell-specific behaviour; they only write text files. Target-side placeholders such as dnf/zypper's `$releasever`/`$basearch` are written out literally and expanded later by the client's package manager, so they are fine.

### Generators in general
- Generators are scripts (Python today, but any language should work) that augment packages at a specific step of the pipeline.
- Every generator reads the contents of `pkggen.yaml` and uses the data relevant to its step.
- Shared functionality for a generator type lives in a `lib.py` file in that generator type's directory.

### Pipeline stages

1. **Distribution list** — `generators/distributions/distributions.yaml` lists every supported distribution with its repology names (`rp-names`) for dependency lookups. Other generators use this list to generate repositories and query dependencies. An rp-name tested as several targets lists their names in `targets` (`void_x86_64: [void-glibc, void-musl]`): those names work wherever an rp-name does (a package's `versions`, `test.distributions.<dist>.versions`, `-t`), and `utils.target_aliases()` / `utils.release_names()` give them to the core.

2. **Repository generators** (`generators/repositories/`) — build the skeleton for a package manager's repository layout (PPA, Gentoo overlay, etc.). Meant to run once: afterwards the repository is the user's to manage. They read the `repositories` key in `pkggen.yaml`. Command: `pkggen gen-repo <distribution>`. Files the repository needs that pkggen doesn't generate (a Gentoo overlay's eclasses and licenses, a landing page, …) are added by hand, or copied in by `gen-repo` from the optional seed folder `repositories.<dist>.seed-files`.

3. **Fetch generators** (`generators/generation/`) — often just called "generators" (a naming leftover from funtoo-metatools; "fetch generator" is the correct term). pkggen scans the top-level keys of `pkggen.yaml`; every key other than `repositories`, `test` and `deployment` is a package group handled by a fetch generator. Each group must have a `generator` key naming a valid fetch generator. A package (or a whole group) is packaged for every distribution with a repository, unless it's locked to some of them with `distributions` (e.g. overlay-only packages); it can also be limited to some releases of a distribution for testing and deployment. The fetch generator queries the user's source control and package repositories for new versions, including binary/source tarballs, and returns the final URLs, alias names and hashes per artifact to pkggen.

4. **Packaging generators** (`generators/packaging/`) — per-distribution toolkit scripts that take everything pkggen now knows about the package's files and produce package files consumable by users and package managers (ebuilds, spec files, PKGBUILDs, …). Output goes into the repository created in stage 2.
   `pkggen generate` = stage 3 + stage 4, and exits once the package files are in the repository.

5. **Testing generators** — `pkggen test`. Each distribution's testing generator gives pkggen a container (or VM) configuration per release it supports; pkggen starts them itself (in a Linux VM when the host isn't Linux), runs the generator's and the user's setup steps from the `test` key in `pkggen.yaml`, builds every package with the distribution's build system, installs it, then runs the post-setup steps from the same `test` key. The `test` key also sets the CPU/RAM budget.

6. **Deployment generators** — `pkggen deploy`. They use the `deployment` key in `pkggen.yaml`. A per-repository, per-distribution-type deployment generator updates the upstream repository with the new packages. Many distributions may not need this step. Deployment usually needs secrets, read from environment variables or the standard secrets file (see below).

### Secrets
Secrets are stored in `$XDG_CONFIG_HOME/pkggen/secrets.yaml` (defaults to `~/.config/pkggen/secrets.yaml`), or `%APPDATA%\pkggen\secrets.yaml` on Windows. Loaded by `load_secrets()` in `generators/generation/lib.py`. Today `github_key` (GitHub), `gitlab_key` (gitlab.com) and `gitlab_keys` (a `{<domain>: <token>}` map for self-hosted GitLab instances) are used by fetch generators, and `git_passwords` / `ssh_keys` (`{<nickname>: <password>}` / `{<nickname>: <private key path>}`), `gpg_keys` / `gpg_passphrases` (`{<nickname>: <fingerprint, armored private key path or the armored key>}` / `{<nickname>: <passphrase>}`), `rsa_keys` / `rsa_passphrases` (`{<nickname>: <PEM private key path or the PEM key>}` / `{<nickname>: <passphrase>}`, for Alpine and Void) and `s3_credentials` (`{<nickname>: {access-key-id, secret-access-key, endpoint?}}`) by deployment generators, which load them with their own `load_secrets()` in `generators/deployment/lib.py` and also accept them from environment variables (`PKGGEN_PASSWORD_<NICK>`, `PKGGEN_SSH_KEY_<NICK>`, `PKGGEN_GPG_KEY_<NICK>`, `PKGGEN_GPG_PASSPHRASE_<NICK>`, `PKGGEN_RSA_KEY_<NICK>`, `PKGGEN_RSA_PASSPHRASE_<NICK>`, `PKGGEN_S3_ACCESS_KEY_<NICK>`, `PKGGEN_S3_SECRET_KEY_<NICK>`, `PKGGEN_S3_ENDPOINT_<NICK>`). pkggen-managed SSH keys live next to it in `keys/`.

### Current state vs. intended design
- Dependencies are only looked up on repology (`generators/dependencies/repology.py`).
- Deployment generators exist for git remotes (`git`), the AUR (`aur`) and S3-compatible buckets (`s3`: Cloudflare R2, AWS, MinIO, …) only. They sign apt/dnf repositories with GPG and Alpine/Void repositories with RSA.
- `pkggen test` only uses containers: VMs are only used to host them on macOS/Windows.

## Architecture (current implementation)

pkggen has six generator layers. All of them are invoked as **subprocesses** (`sys.executable <script>`) that communicate via **JSON over stdin/stdout**; progress and errors go to stderr. Every layer has a `lib.py` with its shared helpers.

### 1. Repository generators (`generators/repositories/`)
Create distribution-specific repository skeletons: `gentoo.py` (overlay: `profiles/`, `metadata/layout.conf`, `repositories.xml`), `rpm-based.py` (rpmbuild tree + optional dnf/zypper `.repo` file), `debian.py` (reprepro APT layout: `conf/distributions`, `conf/options`, `packages/`, optional deb822 `.sources` file), `arch.py` (just a `.gitignore`), `alpine.py` (a `.gitignore`; checks the optional `name`, abuild's repository name, default `pkggen`) and `void.py` (a void-packages style `srcpkgs/`, plus an xbps.d file `<name>.conf` with `repository=<url>` when `name` and `url` are set). Each reads the full `pkggen.yaml` as JSON from stdin and writes into its working directory.

The working directory is `-o` if given, otherwise the repository path: `<pkggen.yaml dir>/pkggen-build/<dist>`, or `repositories.<dist>.path` (relative to `pkggen.yaml`) when set. `utils.get_repo_path()` resolves it; `generate` uses the same function to find the repositories.

Naming convention: generator filename == `name` in `distributions.yaml` == key under `repositories:` in `pkggen.yaml` == packaging generator filename == default template folder (e.g. `rpm-based.py` ↔ `name: rpm-based` ↔ `repositories.rpm-based` ↔ `packaging/rpm-based.py` ↔ `templates/rpm-based/`).

`lib.py` holds the shared helpers: `load_repo_config(dist, required=...)`, `write_file()` (skips existing files unless `PKGGEN_FORCE=1`, which `gen-repo --force` sets; always writes LF), `make_dirs()`, `lines()`, `as_list()`, `to_bool()`, `warn()`/`fail()`. Generators report progress on stderr; stdout is unused.

File contents style: when a file's content is fixed (optionally with f-string values filled in), write it as a `"""\` string literal starting at column 0 and ending with a newline. Use `lib.lines(*entries)` only when the lines are built up in code (conditional appends, loops).

`gen_repo.py` discovers available distributions by cross-referencing `utils.load_distributions()` with the presence of a matching `.py` file in `repositories/`. After the generator, it copies `repositories.<dist>.seed-files` (a folder, relative to `pkggen.yaml`) into the repository byte for byte, keeping existing files unless `--force`; a missing folder is an error before anything is generated. The example seeds the overlay with `eclass/uimgui.eclass` and `licenses/B-Trust-EULA`, and the Debian and RPM repositories with their landing pages (the RPM one is published to the bucket root by a second `deployment.rpm-based` entry, since each Fedora release has its own folder).

### 2. Fetch generators (`generators/generation/`)
`github.py`, `gitlab.py` and `url.py` read one package (JSON) from stdin and print one JSON result on stdout:
```json
{ "version": "1.2.0", "date": "<ISO 8601 UTC, optional>", "tag": "<releases/tags>", "commit": "<commits>",
  "artifacts": [ { "url": "...", "alias": "pkg-1.2.0.tar.gz", "type": "source|asset",
                   "directory": "pkg-1.2.0", "size": 1234, "checksums": { "sha2_256": "...", ... } } ],
  "exports": { "description": "...", "license": "MIT", "homepage": "..." } }
```
`alias` is the unique distfile name, `directory` a best guess of the folder the archive extracts to, `checksums` holds md5, sha1, sha2_224…sha2_512, sha3_224…sha3_512, blake2b and blake2s, `exports` only contains keys the package doesn't set itself. The input also carries `position`, the tqdm bar line to use.

`lib.py`: `run(generate)` (reads stdin, prints the JSON result, turns `TinyError`/network errors into one `Error [pkg]: ...` line on stderr and exit code 1), `session()` (a requests session with the HTTP cache: generators make every request through it), `download_and_hash()` (streams a URL and hashes it in one pass, without decompressing), `http_error()` (messages with URL, status and rate-limit hints), `apply_transforms()`, `to_bool()`, `load_secrets()`, `archive_stem()`.

HTTP cache: `generate.py` sets `PKGGEN_CACHE_DIR` (default `pkggen-build/cache`). `CachingAdapter` stores API answers with their ETag/Last-Modified and asks again with `If-None-Match`/`If-Modified-Since`; a 304 is turned back into the cached answer (GitHub doesn't count 304s against its rate limit). Answers with `Cache-Control: max-age` (repology sends `max-age=3600` and no validators; `no-store`/`no-cache`/`max-age=0` aren't kept) are returned without a request until they're that old (`lib.now()`, patchable), and an expired one is used, with a warning, when the request can't connect. `download_and_hash()` does the same for artifacts and reuses their checksums. The key includes `Accept`/`Authorization`/`PRIVATE-TOKEN`; a broken entry is ignored.

GitHub release queries with `artifacts` download only the listed assets (a missing one is an error); `include-source: true` also adds GitHub's auto-generated tarball. Auto-generated tarballs use `https://<domain>/<user>/<repo>/archive/<ref>.tar.gz`.

`gitlab.py` mirrors `github.py` (same keys and queries, a `gitlab:` block, placeholders `{gitlab_user}`/`{gitlab_repo}`). Differences: `user` may contain subgroups; `domain` (default `gitlab.com`, may include a path prefix) replaces `domain`/`api-domain`; GitLab has no drafts or pre-releases, so `include-upcoming` (releases dated in the future) replaces `include-drafts`/`include-pre-releases`; release `artifacts` are matched against release asset links and use their `direct_asset_url`; auto-generated tarballs use `https://<domain>/<user>/<repo>/-/archive/<ref>/<repo>-<ref>.tar.gz` and extract to `<repo>-<ref>` (leading `v` kept, `/` → `-`); Licensee license keys are mapped to the SPDX ids GitHub reports. The token is only sent to the instance's own host.

### 3. Dependency generators (`generators/dependencies/`)
`repology.py` looks a package's `dependencies` up: input `{projects: [names], repositories: [rp-names], wildcards: [prefixes] (optional, also keeps releases whose name contains one), user_agent}`, output `{projects: {name: {rp-name: [{repo, subrepo, srcname, binname, binnames, visiblename, version, status, summary}]}}, missing: [names], warnings}`. One `GET https://repology.org/api/v1/project/<name>` per project (404 or no known release → `missing`), at least a second apart (`Throttle`, an adapter under the HTTP cache, so cached answers don't wait), one retry after a 429/503 (`Retry-After`, at most 10 s), with pkggen's User-Agent. `lib.py` loads `generation/lib.py` by path for its HTTP cache and errors, and has `trim()`, `version_sort_key()` and `run(main)` (errors are one `Error [dependencies]: ...` line).

`src/pkggen/dependencies.py` is the core side: `check_dependencies()` (called by `check_package()`), `parse_entry()`/`parse()`, `merge()` (a package's lists add to its group's; a package entry replaces the group's entry of the same name), `local_packages()`, `projects()` (what to look up: not pkggen's own packages, not entries every target distribution overrides), `releases()` (the rp-names a package is built for on a distribution: its `distributions.<dist>.versions`, else `test.distributions.<dist>.versions`, else all), `for_job()` and `run_generator()`. `pkggen repology` (`src/pkggen/utilities/repology.py`) runs the same generator and prints every package of the project per release (`-j` JSON, `-i` older releases too, exit code 1 when nothing is found); it caches in `pkggen-build/cache` only next to a `pkggen.yaml`.

### 4. Packaging generators (`generators/packaging/`)
`arch.py`, `debian.py`, `gentoo.py`, `rpm-based.py`. Each reads a job from stdin: `{distribution, package (template context), repository (repositories.<dist>), repository_path, templates_path, templates_root, default_templates_path, run_path, releases (the rp-names the package is built for), dependencies ({build, libraries, runtime, development: [{name, op, version, override? (this distribution's value from pkggen.yaml: a string, or false), local ({name, packaged, package (its pkggen.yaml settings)} for pkggen's own packages) or null, releases: {rp-name: [repology packages]}}]})}`, and prints `{output, files_written, files_unchanged, warnings}` on stdout.

Template folders live next to `pkggen.yaml` in `packages/<dist>/<folder>/`, where `<folder>` is the package's `templates` key (default: the package name). Packages with the same `templates` (usually a group default) share one folder. The Jinja loader searches the folder, then `packages/<dist>/` (`templates_root`), so a folder can `{% extends "uimgui-app/PKGBUILD.tmpl" %}` and override blocks, or `{% include "_base/helpers.sh" %}`; only the package's own folder is rendered. A child template's top-level `{% set %}`s are visible to the templates it extends (the example's `_base` templates take `base_depends` this way). If a folder is missing or has no `.tmpl` files, the generator copies `generators/templates/<dist>/` into it and warns (a missing folder is created in one rename, so packages sharing it can't see half of it); if only some required templates are missing, just those are copied (existing files are never overwritten). Then every `*.tmpl` file is rendered with Jinja2 and every other file is copied:

| Generator | Required templates | Output |
|---|---|---|
| `arch.py` | `PKGBUILD.tmpl` (default also has `.SRCINFO.tmpl`) | `<repo>/<name>/` |
| `debian.py` | `debian/control.tmpl`, `debian/rules.tmpl`, `debian/changelog.tmpl` | `<repo>/packages/<name>/debian/…` (`rules` made executable) |
| `gentoo.py` | `ebuild.tmpl` | `<repo>/<category>/<name>/<name>-<version>.ebuild` + other files, plus a `Manifest` with DIST entries built from `artifacts` (existing entries for other distfiles are kept). `category` comes from the package (or its `gentoo:` block), falling back to the first `repositories.gentoo.categories` entry with a warning; a category that isn't in `categories` only warns when the overlay has no `masters` (it inherits theirs). The version must be a valid Gentoo version |
| `rpm-based.py` | `spec.tmpl` | `spec.tmpl` → `<repo>/SPECS/<name>.spec`, other files → `<repo>/SOURCES/` |
| `alpine.py` | `APKBUILD.tmpl` | `<repo>/<name>/` (an aports-style APKBUILD folder). The template variable `apk_version` is the version in Alpine's syntax (`alpine.pkgver`, else the `apkver` filter's translation; anything else fails with a hint). `alpine.py` defines the format's `VERSION_RE` and `apkver`, and gives its templates the `apkver` filter |
| `void.py` | `template.tmpl` | `<repo>/srcpkgs/<name>/` (`template` + `patches/`, `files/`, …). `xbps_version` is the version without `-`/`_` (`void.version`, else the `xbpsver` filter's translation; `void.py` defines `VERSION_RE` and the `xbpsver` filter) |

Dependencies: every generator calls `lib.dependencies(job, DEPENDENCY_FIELDS, pick, render)` before rendering, which sets the template variable `deps` (always, with empty lists without `dependencies`). `DEPENDENCY_FIELDS` maps each role to `(field, kind)` pairs, kind `main` (the program or library) or `dev` (its development files). Per release, the generator's `prepare(packages)` runs first, if it passes one (Alpine and Void pass `merge_split_packages()`: repology lists every subpackage (`glfw`, `glfw-devel`, …) as its own entry, which it merges into one per source package and version, every `binname` in `binnames`). Then `drop_unwanted(packages, noise, other_targets)` removes the packages a dependency never means, by the generator's own rules, passed as `dependencies(..., noise=NOISE, other_targets=OTHER_TARGETS)`: `NOISE` is a tuple of binary package suffixes (`-doc`, `-dbgsym`, `-debuginfo`, `-openrc`, …; Gentoo has none), `OTHER_TARGETS` a regex (or a function name → bool) for other targets' packages, checked against source and binary names (Arch's `lib32-`, the MinGW toolchains, cross compilers). Then `choose_package()` picks repology's package (its own name (`source_name(package)`, default repology's `srcname`; Gentoo passes one that drops the `category/`), then a current status over `legacy`/`rolling`, then the newest version, then the shortest name), `pick(job, dep, package, kind)` the name from it (`main_package(package, project, dev_suffix, prefixes)`/`dev_package(...)` look at `binnames`: `<src><dev_suffix>`, `<prefix><src><dev_suffix>`, else the main package; each generator passes its `DEV_SUFFIX` (`-dev`, `-devel`), and `prefixes` defaults to `LIBRARY_PREFIXES` (`lib`), with OpenMandriva's `lib64` added by `rpm-based.py`; without binary names (openSUSE Leap) `dev_package()` returns None and `rpm-based.py` guesses), and `render(job, dep, names)` writes the field's value with the version. Overrides are used as they are (`false` drops the entry), local packages go through `local_name()`, or the generator's own `local` (Gentoo: `category/name`, the category read from the local package's `package` settings, falling back to the overlay's first category). Warnings: a release whose version is below the constraint (`satisfies()`, by the leading numbers, epoch dropped), releases without the package; a dependency no targeted release has fails the distribution, naming all of them at once. Warnings are deduplicated. `render` can also be `{field: function}` (Void writes versions only in `depends`).

### 5. Testing generators (`generators/testing/`)
`alpine.py`, `arch.py`, `debian.py`, `gentoo.py`, `rpm-based.py`, `void.py`. They only *describe* containers; `src/pkggen/testing.py` runs them. Each has a `TARGETS` table `{rp-name: {name, image, arches?, ...}}` that must cover exactly the distribution's `rp-names` in `distributions.yaml` (a test checks this). An rp-name with several targets maps to a list of specs, whose names are its `targets` in `distributions.yaml`; an rp-name in `versions` selects all of them, a target name one (`lib.table_specs()`). Input on stdin: `{distribution, repository, test: {setup, post-setup} (the user's steps, global then per distribution), rp_names, versions (null or test.distributions.<dist>.versions), host_arch, packages: [{context, output}]}` (`output` relative to the repository; `packages` is empty when pkggen only asks for the targets). Output: `{targets: [...], skipped: [{name, rp_name}], warnings}` (`skipped`: the releases with no image for `host_arch`, so `-t` can name them and get a warning instead of an "unknown target" error), each target being `{name, rp_name, image, platform, data_images: [{image, path}], env, repo, setup, prepare, packages: [{name, build, install}], finalize, post_setup, collect, publish}`; `env` values may contain `${PKGGEN_JOBS}` (`lib.JOBS`), which pkggen replaces by the job count (Debian sets `DEB_BUILD_OPTIONS=parallel=${PKGGEN_JOBS}`, RPM `RPM_BUILD_NCPUS`, Gentoo `MAKEOPTS`); `publish` (`PUBLISH` in each generator, checked by `testing.publish_problem()`) tells deployment generators how to upload the collected repository: `{indexes: [regexes], metadata: [regexes], content_types: {suffix: media type}}`, the regexes searched in paths inside the target's output (indexes list the packages, metadata is what clients read first, e.g. apt's `InRelease`); a step is `{name, run (sh script), user, workdir}` and runs in its own `sh -exc`. `data_images` are created and run once with `--entrypoint true` (Podman only fills their volumes on first start), so they must contain `true`.

### Running the tests (`src/pkggen/testing.py`, `src/pkggen/containers.py`)
`pkggen test` checks `pkggen.yaml` (`load_test_config()`, one error listing every problem) and the packages, picks the engine (`Engine.detect()`: `--engine`, `test.engine`, else podman then docker, all through their CLIs), and calls `prepare_host()`: on Linux or with a remote host (`test.connection`, `CONTAINER_HOST`, `DOCKER_HOST`) nothing happens. On macOS/Windows with Podman, `ensure_machine()` creates, resizes or starts the rootful `pkggen` Podman machine with the budget, capped by `machine_budget()` to the host's CPUs and to its RAM minus a quarter (at least 2 GiB), with a warning (or uses another machine that's already running on macOS). When pkggen sized its own machine, that machine is the budget: `prepare_host()` clears `cpus`/`memory` so the containers share all of it. WSL machines (the Windows default) are never resized (`podman machine set` can't, they get `.wslconfig`'s resources), so there the budget still limits the containers, with a warning; the VM type comes from `machine list`, which `machine inspect` doesn't report. With Docker, Docker Desktop/Colima must be running. BSDs need a remote host. It then asks every testing generator for its targets, and `plan_resources()` splits the budget: `jobs` containers at once (default `min(targets, cpus // 2, GiB // 2)`), each with `--cpus total/jobs` and `--memory total/jobs` (dropped with a warning when the engine's cgroups lack the controller), and `PKGGEN_JOBS`/`MAKEFLAGS` set to match (the build tools' own variables come from the targets' `env`).

A thread pool of `jobs` workers starts the containers (`run -d --entrypoint sleep … infinity`, labelled `pkggen.session=<id>`) and runs their setup while the main thread runs `generate.run_pipeline()` on the host. Once a distribution's packages are generated, its testing generator is run again with them. Packages whose `distributions.<dist>.versions` leave out a target are dropped from it (`limit_packages()`; they're recorded in `results.json` with `ok: false` and a `skipped` reason, but don't fail the target). Packages are built in `pkggen.yaml` order, each installed before the next one builds, so dependencies between the packages work when they're listed first (e.g. libraries before the framework before the applications); `-p` with only a later package fails if its dependencies aren't in the distribution's repositories. Each worker then copies the repository in (`cp`, which also works with remote engines), runs prepare, then build + install per package (a failure skips that package only), finalize (always) and post-setup (only if nothing failed), and copies `collect` out to `pkggen-build/test/<target>/`, then lists the files of `collect` that are executable in the container (`Engine.list_executables()`: `find <collect> -type f -perm -u+x -print0`), because the copy loses that bit on file systems without one (NTFS). Step output goes to `pkggen-build/test/<target>.log`; the terminal only gets one line per event. Containers are removed at the end, on errors and on Ctrl-C (by label), unless `--keep` is given.

`-t` takes target names or rp-names; pkggen asks the testing generators again for the chosen ones by rp-name, or by target name when an rp-name has several targets (`release_of()`).

`test:` in `pkggen.yaml` (all optional): `engine`, `connection`, `cpus`, `memory` (`16G`, `512M`, or a number of GiB), `jobs`, `vm: {disk}`, `pull` (`always`/`missing`/`never`/`newer`), `setup`/`post-setup` (lists of commands, or `{name, run, user, workdir}`), and `distributions: {<dist>: {versions, setup, post-setup}}`, where `versions` holds rp-names or target names.

When the run ends (not on Ctrl-C), `write_results()` merges every target of the run into `pkggen-build/test/results.json` (`load_results()` reads it): `{"targets": {<target>: {distribution, ok, finished, output (the folder in pkggen-build/test/, or null), packages: {<name>: {version, ok, skipped?}}, publish (the target's), executables?: [POSIX paths relative to output], failed?: [first lines], skipped?: reason}}}` (`executables` is missing when they couldn't be listed; the log says so). Entries of targets that weren't run are kept; releases a testing generator reports as `skipped` (no image for the host's architecture) are written with `ok: false`, also when nothing could run, so an older result can't be deployed.

### 6. Deployment generators (`generators/deployment/`)
`git.py`, `aur.py` and `s3.py` publish what `pkggen test` collected. Input on stdin: `{check, id, where (e.g. deployment.rpm-based[1]), distribution, deployment (its pkggen.yaml block), repository, run_path, work_path (pkggen-build/deploy/<id>/), targets: [{name, path (its test output), ok, reason, packages: {<name>: {version, ok}}, publish (from results.json), executables (from results.json, or null)}], skipped_targets (selected, but with no output), packages (-p, or null), skip_tests, interactive, dry_run}`. With `check: true` a generator only validates its block and prints `{errors, warnings}`; otherwise it prints `{pushed, unchanged, failed: [{name, message}], skipped: [{name, reason}], warnings}`. Progress, warnings and prompts go to stderr; prompts read the terminal itself (`/dev/tty`, `CONIN$`), since stdin carries the job.

- Staging (`lib.stage_targets()`), shared by `git` and `s3`: every target's output goes to its `path` (default `{target}`). Several targets may share a folder (e.g. `path: ""` for one apt repository with a suite per release): identical files merge, a file they have with different content is an error naming both. `exclude` regexes (`re.search` on the path inside the target's output) leave files out, and those paths are never pruned either. When a selected target that isn't deployed this time shares a folder with deployed ones, nothing in that folder is pruned (with a warning). One target's folder can't be inside another's.
- Distribution hooks (`generators/deployment/hooks/<dist>.py`, one per distribution in `distributions.yaml`, a test checks): what depends on the repository format. `lib.run()` loads the job's `distribution`'s hook with `lib.load_hook()` (importlib, once; a missing hook is an error in every mode) as `job.hook`. Every hook defines `SIGNING` (`"gpg"`, `"rsa"` or `None`: which of `gpg-key`/`rsa-key` its repositories use), `OPTIONS` (the extra signing keys it reads, from `lib.HOOK_OPTIONS`: `key-name`, `signed-by`), `check(job, errors)` (its own checks, called by `lib.check_signing()`) and `sign(job, folder, published)` (called by `lib.sign_repository()`). Hooks `import lib`, which `load_hook()` points at the lib that loaded them. `debian`/`rpm-based` only list their metadata files for the generic `lib.sign_gpg()`, `alpine`/`void` sign with `lib.RsaSigner` themselves, `arch`/`gentoo` sign nothing. `check_signing()` makes a key or option the hook doesn't use an error (`gpg-key` on Gentoo, `key-name` on Debian, …).
- Signing (`lib.sign_repository()` → the hook, `gpg-key: <nickname>`, optional `gpg-passphrase: <nickname>` and `public-key: <path in the repository>`): `dists/<suite>/Release` gets `InRelease` + `Release.gpg`, `repodata/repomd.xml` gets `repomd.xml.asc` + `repomd.xml.key` (all armored), signed with SHA-512 by the host's `gpg` (so keys never enter the test containers). A fingerprint uses the user's keyring; an armored key (path or text) is imported into a temporary `GNUPGHOME` in `work_path`, deleted afterwards. A metadata file that didn't change keeps its published signatures, so re-deploying an unchanged repository changes nothing. `public-key` is relative to the repository's root (not a target's folder).
- RSA signing (`hooks/alpine.py`, `hooks/void.py`, `rsa-key: <nickname>`, optional `rsa-passphrase`, `key-name` (Alpine, default `<nickname>.rsa.pub`, must end in `.rsa.pub`), `signed-by` (Void, `"Name <email>"`, required there) and `public-key` (the PEM public key)), for Alpine and Void, with the Python package `cryptography` on the host (`RsaSigner`, PKCS#1 v1.5, SHA-256; imported lazily, checked by `check_signing()`). Alpine: in every folder with an `APKINDEX.tar.gz`, each `.apk` and the index get their leading `.SIGN.*` gzip member (the test's throwaway signature) replaced by `.SIGN.RSA256.<key-name>` (a cut tar like `abuild-tar --cut`, signing an `.apk`'s control member or the rest of the index), so the index's package checksums stay valid. Void: every `<arch>-repodata`'s packages get `<pkg>.xbps.sig2`, and its `index-meta.plist` gets the public key, its size and `signed-by` (written as `xbps-rindex --sign` does); the repodata must be xz/gzip/bzip2/uncompressed (zstd is an error), and keeps its compression and other files. Unchanged files keep their published bytes. Each distribution takes only its hook's key; `lib.signs(job)` says whether either is set.
- `git.py` (`deployment.<dist>: {generator: git, url, username, email, ssh-key | password | managed-key, branch, targets, path, prune, preserve, exclude, message, sign, gpg-key, gpg-passphrase, rsa-key, rsa-passphrase, key-name, signed-by, public-key}`): skips targets that failed their tests (`job.usable_targets()`, unless `skip_tests`), fetches the upstream into `work_path` (a pkggen-owned clone that is reset and cleaned every run; an empty remote gets an orphan branch; `branch` defaults to the remote's HEAD, else `main`), stages the targets (signed into `<work_path>.signed` with `gpg-key` or `rsa-key`), copies them over the checkout overwriting changed files and keeping executable bits, then commits as `username`/`email` and pushes (never forced; if the upstream moved meanwhile, everything is redone once on top of it). The staged modes follow each target's `executables` (`executable_modes()` + `set_modes()`: `git update-index --chmod=±x` after `git add -A`), so on Windows, where the output has no executable bits and Git has `core.filemode=false`, files still land as 100755 (and lose it when they're no longer executable), like on Linux; without the list the file system decides as before. Files that only exist upstream are kept unless `prune: true`, which deletes them except paths where the file or a parent folder matches a `preserve` regex (`re.search` on the POSIX path relative to the root), excluded paths, and the folders of selected targets that aren't deployed this time. Commits aren't signed unless `sign: true` (`-c commit.gpgsign=false`), because signing keys that need a passphrase or a touch can't prompt there. Every git command gets `-c core.autocrlf=false -c core.longpaths=true` (`GIT_OPTIONS`), so files go upstream byte for byte even with Git for Windows' system-wide `autocrlf=true`, and paths over 260 characters (createrepo_c's `repodata/<sha256>-…`) can be added. `--dry-run` commits in `work_path` without pushing. `-p` doesn't apply (warning).
- Auth (`auth_env()`): `https` URLs with `password` get a `credential.helper` set through `GIT_CONFIG_COUNT/KEY_n/VALUE_n` that prints `$PKGGEN_GIT_USERNAME`/`$PKGGEN_GIT_PASSWORD` (the URL's user, else `username`), after an empty helper that clears the user's own; the secret is never on a command line or on disk. SSH URLs (`git@host:path`, `ssh://`) use `GIT_SSH_COMMAND="ssh -i <key> -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new"` (+ `BatchMode=yes` without a terminal) with the `ssh-key` nickname's key, else a pkggen-managed key named `managed-key` (default `git-<host>`). Local paths and `file://` need nothing.
- `s3.py` (`deployment.<dist>: {generator: s3, bucket, endpoint, region, credentials, addressing, path, targets, prune, preserve, exclude, gpg-key, gpg-passphrase, rsa-key, rsa-passphrase, key-name, signed-by, public-key}`): for S3-compatible storage (Cloudflare R2, AWS S3, MinIO, B2). Requests are signed with AWS Signature Version 4 by its own small client on `requests` (`sign()`, checked against AWS's published examples; no SDK, so the HTTP mocks work). Path-style URLs (`<endpoint>/<bucket>/<key>`) with an `endpoint` (`region` defaults to `auto`, as R2 wants), virtual-hosted ones on AWS without it (`region` default `us-east-1`); `addressing` overrides it. `credentials` names `s3_credentials` (or the `PKGGEN_S3_*_<NICK>` variables, which may also give the endpoint), else `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`. It applies the test gate, stages and signs into `work_path/stage`, lists the bucket under every target folder (`ListObjectsV2`), and uploads the files whose MD5 differs from the object's ETag with `Content-MD5`: packages first, then the indexes, then the metadata, as each target's `publish` names them (`Layout`, which matches a path against every target whose folder holds it; a target without `publish`, from an older `results.json`, warns and is uploaded in name order). Indexes and metadata get `Cache-Control: no-cache`; content types come from `publish`'s `content_types`, else `.asc`/`.gpg`/`.zst` and `mimetypes`. So clients never see an index that points at a missing file, and `s3.py` knows no repository format. With `prune`, objects no target has are deleted last (same exceptions as `git`). `--dry-run` lists what would be uploaded and deleted.
- `aur.py` (`deployment.arch: {generator: aur, username, email, ssh-key | managed-key, targets, prune, preserve, message, sign}`; `url`, `branch`, `password`, `path` are errors) loads `git.py` by path (`import git` could find GitPython) and reuses `auth_env()`/`deploy_tree()`. It deploys every PKGBUILD folder of the first target's output (`pkggen-build/test/arch/<name>/`, not the `x86_64/` pacman repository; executable bits from `Target.executables_in(<folder>)`), one after another, each to `ssh://aur@aur.archlinux.org/<pkgbase>.git` on `master` (fetched anonymously from `https://aur.archlinux.org/<pkgbase>.git`, work clone `work_path/<pkgbase>`). Packages that failed or weren't tested are skipped unless `skip_tests`; a folder without `.SRCINFO` or with subfolders (the AUR rejects both) fails only itself, as does a failed push. `pkgbase` and the version (`[epoch:]pkgver-pkgrel`) come from `.SRCINFO`; `message` defaults to `Update to {version}` (`{name}` and `{version}` are replaced). Without `ssh-key` it uses the managed key `aur` and tells the user to add it at `https://aur.archlinux.org/account/<username>/edit`.
- Managed keys (`lib.managed_key(job, name, where_to_add)`): `<config dir>/pkggen/keys/<name>` (+ `.pub`, + `.json` with `created`/`expires`), made with `ssh-keygen -t ed25519 -N ""` and valid for 90 days (`KEY_LIFETIME`). Less than a week left (`KEY_WARNING`) → a warning; expired → a new key, and the old one's fingerprint to remove. After making a key pkggen prints the public key and where to add it, then waits for Enter when `interactive`, or fails that deployment with the instructions. A key without its `.json` counts from the file's modification time.

`lib.py`: `Job` (`usable_targets()`, `warn()`, `say()`, `key()`), `Target`, `DeployError`, `load_secrets()`, `secret_password()`, `secret_ssh_key()`, `secret_problem()`, `managed_key()`, `wait_for_user()`/`open_console()`, `check_keys()`, `check_string()`, `check_patterns()`, `check_signing()`, `load_hook()`/`HOOK_OPTIONS`, `normalise()`/`under()`/`preserved()`, `stage_targets()`/`Staged`/`write_staged()`, `sign_repository()`, `sign_gpg()`/`Signer`, `RsaSigner`, `finish_signing()` (the warning when nothing was signed, and `public-key`), `read_relative()`/`write_relative()`, `signs()`, `now()`, `run(main, check)`. `git.py` also exposes `url_kind()`, `prepare()`, `sync()`, `commit()`, `deploy_tree()` and `check_common()` (identity, auth, `prune`/`preserve`/`exclude`/`sign`/signing checks shared with `aur.py`).

### Deploying (`src/pkggen/deploy.py`)
`pkggen deploy` loads `deployment` (`load_deployments()`: every `deployment.<dist>` is a mapping or a list of them, each with a `generator` in `generators/deployment/` and optional `targets`; ids are `<dist>-<generator>`, then `-2`, `-3`…; one error lists every problem), checks `-p` names with `generate.load_packages()`, needs `results.json` (generators check for their own tools: `git.py`'s `check_common()` reports a missing `git`, also for the AUR). `select_targets()` picks each deployment's targets (`targets`, else every target of its distribution in the results, narrowed by `-t`); targets without output are reported as skipped and passed as `skipped_targets`, the others are passed with their `ok`/`reason`/`publish` (the generators apply the gate, per target for git and per package for the AUR). Then every generator runs in check mode (one error for all), and the deployments run one after another with stderr shown live (and kept for the summary). A failure doesn't stop the other deployments. The summary counts pushed (or "would be pushed" with `--dry-run`) and up-to-date repositories and lists every failure and skip; the exit code is 1 if there's any.

### Orchestration (`src/pkggen/generate.py`)
`pkggen generate` loads every package group (every top-level key except `repositories`, `test`, `deployment`), validates them all up front, then runs the fetch generators in a thread pool (up to 10). Meanwhile one dependency-generator run looks up every selected package's `dependencies` (in a third, one-thread pool); with `-p`, pkggen's own packages outside the filter still count as local. As each fetch finishes, it builds the template context and submits one packaging job per target distribution to a second pool (`os.cpu_count()` workers), so packaging overlaps with downloads; jobs of packages with `dependencies` wait for the lookup, and fail (only those) when it fails. Targets are distributions that have a packaging generator **and** a `repositories.<dist>` block; a missing repository directory is reported with a hint to run `gen-repo`. A package is only packaged for the targets its `distributions` allow (`builds_for()`); a package left with none gets a warning and is only fetched. Failures never cancel other jobs; a summary lists them at the end and the exit code is 1. `run_pipeline(config, package_filter, distribution_filter)` does the work and returns a `PipelineResult` (`packages`, `targets`, `contexts`, `packaged`, `failures`, `stats`), so `pkggen test` can reuse it.

### Config files
- **`pkggen.yaml`** (project root) — defines package groups and repository metadata. Top-level keys other than `repositories`, `test` and `deployment` are package groups, each requiring a `generator` name and a `packages` list. Other keys of a group are defaults for its packages, deep-merged under each package's own keys, except `maintainer` and `author`, which can only be set per package (a group that sets them is an error). Optional package fields every packaging generator reads (checked up front by `check_package()` in `generate.py`):
  - `maintainer`: string, `"Name <email>"`. The packager: Debian `Maintainer:` and changelog trailer, PKGBUILD `# Maintainer:` header, RPM `%changelog`, Gentoo `metadata.xml` `<maintainer>` (needs the email, else the overlay `owners` are used).
  - `author`: string, `"Name <email>"` or just a name. Upstream author: Debian `copyright` `Copyright:` field, Gentoo `metadata.xml` `<upstream><maintainer>`.
  - `templates`: the template folder in `packages/<dist>/` (default: the package name), so packages can share templates; usually a group default.
  - `distributions`: the distributions the package is packaged for (default: all). A list of names (`[ gentoo ]`), or a mapping that can also limit the releases it's tested and deployed on: `{ arch: {}, debian: { versions: [ debian-unstable, ubuntu-26.04 ] } }`. `versions` takes rp-names or target names (compared normalised: `ubuntu-24.04` = `ubuntu_24_04`, checked against `distributions.yaml`).
  - `dependencies`: `{build, libraries, runtime, development}` lists (all optional) of repology project names (`pkggen repology <name>`), each `"<project>"` or `"<project> <op> <version>"` (`>=`, `<=`, `=`, `>`, `<`), or a mapping `{name, version: "<op> <version>", <distribution>: "<its name there, used as it is>" | false}`. `build`: tools needed to build; `libraries`: linked against, so their development files are needed to build (the runtime library is found by `dh_shlibdeps`/rpm's automatic dependencies); `runtime`: needed to run; `development`: development files needed to build and to run (libraries the package's users compile against). A name that is one of pkggen.yaml's packages is that package. A package's lists add to its group's (`dependencies.merge()`). Validated by `dependencies.check_dependencies()`.
  - `architectures`: `"any"` (builds on every architecture) or a list of names, default `[amd64, arm64]`. Each packaging generator translates it with `lib.architectures(job, names, any_value, other=None)` into the template variable `arches`: arch → `x86_64`/`aarch64`, `any` → `['any']`; debian → `amd64`/`arm64`, `any` → `any`; rpm-based → `ExclusiveArch: %{?x86_64}%{!?x86_64:x86_64} aarch64` (the `%{x86_64}` macro where it's defined, because OpenMandriva builds x86_64 as `znver1`), `any` → no `ExclusiveArch`; gentoo → `~<arch>` keywords, other names passed through, `any` → every main Gentoo arch; alpine → `x86_64`/`aarch64`, `any` → `all`; void → `x86_64*`/`aarch64*` (the `*` covers musl), `any` → no `archs`. Names a generator doesn't know are dropped; if none is left it fails. Packages without compiled code override it per distribution (`debian: { architecture: all }`, `arch: { arch: [any] }`, `alpine: { arch: noarch }`, `void: { archs: noarch }`, `BuildArch: noarch` in the spec).
- **`$XDG_CONFIG_HOME/pkggen/secrets.yaml`** (default `~/.config/pkggen/secrets.yaml`; `%APPDATA%\pkggen\secrets.yaml` on Windows) — API keys and deployment secrets. Currently used keys: `github_key` for authenticated GitHub API requests, `gitlab_key` for gitlab.com and `gitlab_keys: { <domain>: <token> }` for other GitLab instances; `git_passwords`, `ssh_keys`, `gpg_keys`, `gpg_passphrases` and `s3_credentials` for deployments (see Secrets).

### Template context
Templates see the package's own `pkggen.yaml` keys at the top level (`name`, `github.user`, `maintainer`, …), plus:
- `version`, `date` (datetime), `tag`, `commit`, `artifacts` (fetch output), `source` (= `artifacts[0]`)
- `description`, `license`, `homepage` (package value, else fetch `exports`)
- `distribution`, `repository` (its `repositories.<dist>` block), `now`
- `template_dir`: the template folder relative to `pkggen.yaml` (`packages/arch/cmake-library`), for "edit … instead" comments
- `dist`: the package's own `<distribution>:` block, e.g. `arch: { depends: [glibc] }` → `dist.depends`
- `deps`: the package's `dependencies` in this distribution's names (see the packaging generators' table): add `dist`'s lists to them in templates
- `architectures` (default `[amd64, arm64]`) and `arches`, its translation for this distribution
- `apk_version` (Alpine) and `xbps_version` (Void): the version in the format's syntax
- `maintainer` and `author` are undefined when not set: use `maintainer | default("Your Name <you@example.com>")`

Filters: `spdx` (deprecated GitHub SPDX ids → current ones), `shquote`, `dquote`, `person_name`/`person_email` (`"Jane <j@x.org>"` → `Jane` / `j@x.org`). Only in their generator's templates (its `FILTERS`): `pkgver` (Arch and RPM: `-`, `:`, `/`, whitespace → `_`), `debian_license` and `rfc2822` (Debian), `gentoo_license` (Gentoo), `rpmdate` (RPM), `apkver` (Alpine: `v1.0-rc1` → `1.0_rc1`, `2.0.0-beta.2` → `2.0.0_beta2`), `xbpsver` (Void: `-`, `_`, `:`, `/`, whitespace → `.`).

### The example (`example/`)
The real configuration of the UntitledDesktop project (MadLadSquad): six CMake libraries, the framework (with UVKBuildTool), three applications built with UVKBuildTool, and two Gentoo-only overlay packages (`abcccid` from GitHub, `btrustbiss` from a fixed URL locked with `hash-locks`), for all six distributions, with real `test` and `deployment` blocks (AUR, the overlay on GitHub, and Cloudflare R2 for RPM/DEB/APK/XBPS: Alpine per release in `{target}/<arch>/`, Void's glibc and musl in one `binpkgs/`, both signed with the RSA key `madladsquad-rsa`). Its group order is the build order. Dependencies are in `dependencies:` blocks (overrides only where repology's name doesn't fit: Gentoo's `virtual/pkgconfig` and USE dependencies, RPM's `pkgconfig` capability, Debian's `golang-go`/`x11-xserver-utils`, `cargo`, Alpine's `mesa-dev` for libglvnd); the templates only add each distribution's toolchain (`gcc-libs glibc`, `gcc-c++ make`, Debian's framework needs `cmake pkgconf` at runtime) and the Gentoo-only packages keep theirs in their ebuilds. The uimgui eclass already depends on the framework, CMake and pkgconfig, so the applications' entries for them are `gentoo: false`. Templates: `packages/<dist>/_base/` (only extended, never a package's folder), `cmake-library/` and `uimgui-app/` (shared through `templates`), and own folders for the framework and the applications with Go/Rust parts, which extend `uimgui-app`. `repository-files/` holds the seed files. The Alpine templates run under busybox `sh` (no brace expansion) and add GNU `sed` to `makedepends` (the scripts use its extensions); abuild makes CMake use Ninja (`CMAKE_GENERATOR`), so the libraries build with `samurai` and the framework and applications, whose scripts run `make`, export `CMAKE_GENERATOR="Unix Makefiles"`; the framework's scripts (also the installed `export.sh`) are bash scripts, so it needs `bash` to build and to run; the Void cmake-library template uses xbps-src's `build_style=cmake`. Upstream workarounds the templates carry, until upstream fixes them:
- Older library releases install to a hardcoded `lib64/` (and their `.pc` to `lib/pkgconfig`): a prepare step switches them to `GNUInstallDirs` (newer releases already use it, then it does nothing).
- UVKBuildTool hardcodes `lib64/`; `uvproj.yaml`'s `install-override.unix.framework-library-dir`/`framework-application-library-dir` and a `lib64/` → libdir rewrite put everything in the distribution's libdir. The directories are compiled in, so files must never be moved afterwards.
- `UVKBuildTool --build` exits with 0 when the build fails: every template checks that `lib<project name>Lib.so` was installed.
- The framework has no install step of its own: it's installed by building an empty project (`pkg`) with `install-framework: true`, whose files are then removed.
- The framework's build scripts (`install.sh`, `export.sh`, `create-project.sh`, `UVKBuildTool/ci.sh`) run `make -j <every CPU>` and ignore `MAKEFLAGS`, which runs out of memory in the test containers. The framework package patches them to honour `UIMGUI_JOBS` (the installed `export.sh` builds the applications too), and every template sets it from the distribution's own setting: `MAKEFLAGS` (Arch), `%{_smp_build_ncpus}` (RPM), `DEB_BUILD_OPTION_PARALLEL` (Debian), `makeopts_jobs` (Gentoo).
- The framework needs GLFW ≥ 3.4 with both its X11 and Wayland backends (it calls the Wayland functions unguarded), so Wayland is an explicit dependency, Gentoo needs `media-libs/glfw[X,wayland]` (set in the example's `test.distributions.gentoo.setup`), and the framework and applications skip Ubuntu 24.04 (GLFW 3.3) through `distributions`. UGM also skips Debian 13 (Go 1.24; its Incus bindings need 1.25).
- Debian: `dh_fixperms` makes `/usr/include` files 0644, so the framework restores `export.sh`'s execute bit; `dh_clean` deletes `*.orig`, so ibus-handwriting keeps its vendored crates' `Cargo.toml.orig` (their checksums cover it).
- musl (Alpine, Void musl): UntitledExec's `uexecdata.h` uses `pid_t`/`size_t` without including `<sys/types.h>`/`<stddef.h>` (glibc pulls them in through other headers): the Alpine and Void cmake-library templates add them when they're missing.
- Void: xbps-src's `14-fix-permissions` hook makes `/usr/include` files 0644 like `dh_fixperms`, so the framework's template sets `nofixperms=yes` (the applications run the installed `export.sh`).
- Libraries that bundle a dependency (i18n's rapidyaml, open's file dialog library) are built with `-DBUILD_SHARED_LIBS=OFF`: Fedora's `%cmake` and Gentoo's `cmake.eclass` turn it on, which makes the bundled library a shared one that isn't installed.

### Adding a new fetch generator
1. Create `generators/generation/<name>.py`: define `generate(package) -> dict` returning the output contract above and end with `lib.run(generate)`. Log only to stderr.
2. Reference it as `generator: "<name>"` in `pkggen.yaml`.

### Adding a new repository generator
1. Create `generators/repositories/<name>.py` — get its config with `lib.load_repo_config("<name>")`, write files into `cwd` with `lib.write_file()`.
2. Add `- name: <name>` to `generators/distributions/distributions.yaml` with its repology `rp-names` (and optional `rp-names-wildcards`).
3. Create `generators/deployment/hooks/<name>.py` with `SIGNING`, `OPTIONS`, `check(job, errors)` and `sign(job, folder, published)` (see the deployment generators; `arch.py` is the one that signs nothing).

### Adding a new testing generator
1. Create `generators/testing/<name>.py` (same name as the packaging generator) with a `TARGETS` table covering every rp-name of the distribution (a list of specs for an rp-name tested as several targets, named in `distributions.yaml`'s `targets`), and a `main(job)` that returns `[lib.target(job, rp, spec, setup=..., prepare=..., packages=[{name, build, install}], finalize=[..., lib.collect_step()], env={...}, publish=PUBLISH)` for `lib.select_targets(job, TARGETS)`; end with `lib.run(main)`. Set the build tools' parallelism in `env` with `lib.JOBS` (`${PKGGEN_JOBS}`), and describe the repository `finalize` builds in `PUBLISH` (its indexes and metadata, and the content types of its packages), so deployment generators don't need to know the format.
2. Use fully qualified image names (`docker.io/library/…`), so podman never asks which registry to use.

### Adding a new deployment generator
1. Create `generators/deployment/<name>.py` with `check(job) -> [errors]` (start with `lib.check_keys()`; messages name keys with `job.key("...")`) and `main(job)`, which fills `job.pushed` / `job.unchanged` / `job.failed` / `job.skipped` (or raises `lib.DeployError` when nothing can be deployed); end with `lib.run(main, check)`. Respect `job.dry_run`, apply the test gate (`job.usable_targets()` or the per-package `ok`) unless `job.skip_tests`, and keep scratch files in `job.work_path`. Check for the tools it needs in `check()` (pkggen's core doesn't know them), and take what depends on the repository format from the targets' `publish` rather than hardcoding it.
2. Reference it as `deployment.<dist>.generator: "<name>"` in `pkggen.yaml`. A generator that pushes with git can reuse `git.py` by loading it by path, like `aur.py` does.

### Adding a new dependency generator
1. Create `generators/dependencies/<name>.py` with the same input and output as `repology.py` and end with `lib.run(main)`; make its requests through `lib.fetch`'s HTTP cache.
2. Point `dependencies.GENERATOR` in `src/pkggen/dependencies.py` at it.

### Adding a new packaging generator
1. Create `generators/packaging/<name>.py`: set `job.context["arches"] = lib.architectures(job, {"amd64": ..., "arm64": ...}, <any value>)`, call `lib.dependencies(job, DEPENDENCY_FIELDS, pick, render, noise=NOISE, other_targets=OTHER_TARGETS)` (the roles' fields, how to name a repology package, how to write one with its version, the suffixes of the distribution's binary packages that are never a dependency: `-doc`, debug symbols, …, and its other targets' packages: multilib, cross compilers; add `prepare=`, `source_name=` or `local=` when repology's entries or the format's names need it, and pass `main_package()`/`dev_package()` the format's `DEV_SUFFIX` and library prefixes in `pick`), call `lib.ensure_templates(job, REQUIRED)`, set `job.output`, call `lib.render_tree(job, place, filters=...)` with a `place(rel) -> absolute path` mapping (and the format's own template filters, e.g. a version filter made with `lib.substitute()`, its date or license names; keep the format's version syntax regex in the generator too), and end with `lib.run(main)`.
2. Add the default templates in `generators/templates/<name>/`, with `deps` added to the `dist` lists. Keep them language-neutral: no build-system-specific build/install steps or build dependencies (pkggen packages projects in any language), keep the build functions as empty, commented-out stubs (e.g. `#build() {` / `#}`).

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
